# r027：n=8 顶行完成数的分层 IE 资源与算法设计

日期：2026-11-17（Asia/Shanghai）。本轮只做精确资源估计和 n≤6 原型；**没有启动
n=8 计算、没有连接远端，也没有改动 r026 材料或仓库**。

## 计数对象与整数位宽

从顶行 \(T\) 出发的完成数 \(H_T=h(T)\) 可用既有 boundary-completion 的独立峰
容斥表示。对 \(P_8\square P_8\)，删去初始顶行及其邻行后，容斥集合是 6×8
矩形。独立集按大小 \(k\) 的精确层数由行转移给出，总数为
851,302,029，最大层为 \(k=12\) 的 162,959,262 个状态。

对固定独立集 \(I\)，递推
\[
C(I)=\frac{\sum_{v\in I}C(I\setminus\{v\})}{|I\cup N(I)|}
\]
只读 \(k-1\) 层。此处剩余可标号顶点数为 56，所以 \(C(I)\le56!\)，其二进制
长度为 249；而 \(\sum_{v\in I}C(I\setminus\{v\})\le24\cdot56!<2^{256}\)，
故每个递推值与分子都可安全保存在 U256。最终容斥的粗界为
\(851302029\cdot56!<2^{279}\)，因此正、负累加器必须用 U320（或 `cpp_int`），
不能复用 U256 断言为充分。

完整层直方图、每个过渡的模型字节数见 [layer-estimate.json](layer-estimate.json)。

## 可行的低内存布局

不使用旧程序的“全部 mask + C + unordered_map”模型（其估算 31.713 GiB，超出
MacBook 的 24 GB 统一内存）。建议的生产布局是：

1. 以行掩码递归按确定顺序枚举第 \(k\) 层；只保存当前 `C[k]` 和前层 `C[k-1]`
   两个 U256 向量。
2. 前层建立自制的开放寻址表：两条平行数组 `uint64_t key[]` 与 `uint32_t index[]`。
   不使用 `unordered_map`，避免节点和 bucket 的不可控开销。
3. 当前层完成后释放前层值与其哈希表；以完全相同的确定性行枚举第二次扫描当前层，
   将 `mask -> position` 插入新表。这避免保留当前层 mask 向量。
4. 计算阶段哈希只读；若并行，递归前缀通过精确 suffix-count 分块，每个线程写不同
   的当前值范围。第二次建表可先串行，避免开放寻址碰撞的写竞争。

峰值发生在 11→12 层：两个值数组共 10,329,411,904 B，加上 2^28 个槽的平行表
（键 2 GiB、索引 1 GiB），有效载荷为 13,550,637,376 B = **12.620 GiB**，负载率
0.5954。这个数字不含 allocator、线程栈和系统内存；安全运行条件应至少是启动前有
17 GiB 可用统一内存，且占用约 4 GiB 的 GPU 工作已停止并确认释放。否则不启动。

两种无哈希备选均较差：仅存排序前层 mask 的有效载荷峰值约 10.811 GiB，但需要约
267,500,933,028 次二分比较；行转移直接求 rank 虽可只保存两个值数组，却为每次前驱
查找引入多个行状态/候选掩码扫描。原递推本身已有 9,876,689,636 个前驱查找，因而在
没有新的 O(1) rank 公式前，紧凑哈希是可行性与总时长之间较稳妥的选择。

## n≤6 原型核验

`completion_layer_prototype.cpp` 实现了上述“相邻两层值 + 前层开放寻址 + 当前层
确定性重枚举建表”的骨架，并明确拒绝 `n>6`。它使用 U256 递推和 U320 容斥累加；没有
Boost 依赖。实跑结果：

| n | 原型 \(H_T\) | 对照 |
|---|---:|---|
| 3 | 156 | 相等 |
| 4 | 4,213,440 | 相等 |
| 5 | 153,450,311,313,600 | 相等 |
| 6 | 20,779,014,929,894,865,426,585,600 | 相等 |

`verify_prototype.py` 读取这些 JSON 并给出 `all_match=true`。n=6 原型峰值 RSS
3,047,424 B、0 swaps；小规模运行不能外推 n=8 的运行时间或内存。

## n=8 实施前必须修复的边界

现有 `completion_ie_selected.cpp` 用 `(Mask(1)<<N)-1` 构造 `FULL`，在 n=8 时会发生
64 位移位，属未定义行为；n=8 实现必须改为 `FULL=~Mask(0)`。行掩码嵌入和 bit=63
也必须始终从无符号 `Mask(1)` 出发。生产版还须：显式内存预检/上限、逐层进度与
异常回收、每层整除断言、U320 溢出检查、n≤6 交叉后才允许 n=8。

本报告是有限精确计算的资源/实现计划，不构成任何渐近结论或原双峰问题的解决。

## r027 模素数滚动实现（后续修订）

为降低每个层值的存储，`completion_layer_mod.cpp` 改为每次只在一个素数模数下计算。
采用经 `prime_audit.py` 的确定性 64 位 Miller--Rabin（bases
`2,325,9375,28178,450775,9780504,1795265022`）核验的四个素数：

\[
9223372036854775783,
9223372036854775643,
9223372036854775549,
9223372036854775507.
\]

它们均大于 56，因此所有递推分母 \(|I\cup N(I)|\le56\) 在各域中可逆。四者乘积
为 252 bit，严格大于 \(56!\) 的 249 bit；而 \(0\le H_T\le56!\)，所以四个完整
pass 的残数能由 CRT 唯一恢复整数 \(H_T\)。每个 pass 只保存两个 `uint64_t` 值层，
峰值层值数组为 2.405 GiB；与重枚举的 2^28 槽平行哈希表合计有效载荷约 **5.405 GiB**。
残数 JSON 只在完整 pass 成功后以临时文件 rename 写入；已完成素数的 JSON 是可复用的
checkpoint，重启时仅需补缺少的素数 pass，不保存巨大的中间层。

实际 n=3--7 各四个模 pass 已完成。`crt_verify.py` 以任意精度 Python CRT 恢复：
n=3--7 全部等于既有精确值，n=7 得
\(23386940526059745800104592446335589635840\)。四个 n=7 pass 各为 0.41--0.44 s
wall、约 57.7--58.8 MB RSS、0 swaps（6 个 CPU 线程）；这是实际有限资源证据。
按前驱查找数从 n=7 的 31,943,826 到 n=8 的 9,876,689,636，简单比例为约 309 倍，
只可作为约两分钟/prime 的缓存理想下限，绝不能替代 n=8 的首层实测；n=8 的 5.405 GiB
随机查表会处在完全不同的内存带宽区间。

该程序默认拒绝 n=8，只有显式 `--enable-n8` 才接受；本轮没有使用该开关。
`--boundary-test` 实际构造 8×8 的闭邻域，验证 `FULL=~Mask(0)`、top mask `0xff`、
bit 63 以及角点 63 的 55/62/63 闭邻域，从而避免旧式 `(1ULL<<64)` 的未定义行为。

## v2 资源修正与逐层保护

初版模程序曾以 `cap>=2*want` 分配表；对 159,834,860 个前层状态，这实际会取
\(2^{29}\) 槽，而不是报告模型中的 \(2^{28}\) 槽。因此初版不得用于 n=8，且其源
快照保留为 `completion_layer_mod_v1.cpp`（SHA 在 `mod-v1-source-sha256.txt`），不再
作为生产源。

新冻结 `completion_layer_mod.cpp` 显式采用
`while (5*cap < 8*want) cap <<= 1`，即负载率不超过 \(5/8\)。故 11→12 层恰为
\(2^{28}\) 槽、负载率约 .5954；键/索引平行数组为 3 GiB，两个标量值层为 2.405 GiB，
有效载荷为 5.405 GiB。每次分配前程序分别计算并检查：

\[
 8(|C_{k-1}|+|C_k|)+\operatorname{hashBytes}(C_{k-1})
\]

（计算阶段）以及 \(8|C_k|+\operatorname{hashBytes}(C_k)\)（重建阶段），二者均须
不超过默认 7 GiB；JSON 写入实际最大模型 payload。每层 stderr 写出层号、count、
旧和新 hash 容量、两阶段 payload bytes 与耗时。当前层只由互不重叠的前缀块写入，
所有线程只读前层表；哈希重建串行，从而没有开放寻址写竞争。

递归枚举此前仅用 `popcount(row)<=remaining`，现在启动前完整预计算
`(row,previous-row-mask,remaining)` suffix 表；枚举在该表给出零时立即剪枝，表在线程
启动前冻结且只读。由于仅删去零完成数分支，枚举顺序不变；块计数、写入长度及重枚举
hash 索引均有断言。

v2 在 n=3--7 的 20 个 pass 上再次以 CRT 全部恢复既有精确值。n=7 prime 0 的逐层峰值
模型为 38,183,160 bytes，实测 RSS 57,524,224 bytes、0 swaps、0.25 s wall；其他三个
prime 同样通过。n=8 仍未运行，且修复前后均不得把 n=7 的缓存内行为当成 n=8 的性能证明。

## 素性与 CRT 的可复查证书

本机没有 SymPy 或 `factor` 工具，未安装任何依赖。`pratt_generate.py` 用固定参数的
纯标准库 Pollard--Rho 仅生成候选分解树；生成器不是认证依据。最终
`pratt_verify.py` 独立读取 `pratt-certificates.json`，对 49 个节点递归核验：

1. 每个节点的 \(p-1\) 因子及幂次乘积恰为 \(p-1\)；
2. 每个因子节点已递归认证（基例仅 \(2\)）；
3. 见证 \(a\) 满足 \(a^{p-1}\equiv1\pmod p\)，并且对每个不同素因子 \(q\mid p-1\)，
   \(\gcd(a^{(p-1)/q}-1,p)=1\)。

这是完整分解下的 Lucas/Pratt 判据，因此四个 63 位模数的素性由 JSON 证书和纯标准库
验证器承担，而非仅依赖 Miller--Rabin bases。`prime_audit.py` 另以整数精确检查四模乘积
严格大于 \(56!\)。v2 的 `--plan-n8` 在不分配任何层数组的情况下运行相同 payload guard，
输出 11→12 计算阶段 5,803,578,448 B、重建阶段 4,524,899,568 B，均低于 7 GiB。
