# 现有 fixed_root_smc 对 n=16 的静态可行性审查

结论：**不能简单把现有源码的 n=11 参数改为 n=16 运行**，本轮没有修改或启动
n=16 版本。

硬阻塞如下：

1. `G::adj` 与 `W::a` 的容量固定为 121，且入口显式拒绝 `n>11`；n=16 要
   (N=256) 个顶点。
2. 状态集合使用单个 `__uint128_t H`，而 `allowed` 构造
   `(H(1)<<g.N)`。对 (N=256) 既不能表示顶点集合，也会导致非法移位；必须改为
   至少四个 64-bit limb 的定长 bitset，并逐处重审集合差、邻接和位扫描。
3. 当前 MH 每提案线性扫描长度 `r` 以找 `v`，并调用线性 `valid`。n=16 不但
   要扩大状态宽度，还需要维护位置反查/前缀邻接计数，才能避免每提案的
   (O(N)\) 代价。
4. 现行 normalizer 累乘保存在 `double Z`。已知 n=16 的 \(h_r\) 量级约
   \(10^{419}\)，远超 double 最大约 \(10^{308}\)，因此即使位集扩容也会溢出。
   新核必须采用 `logZ`（含稳定的 replicate/ratio 汇总）或明确的逐层概率
   归一化账本，且重新验证其统计含义。

即使只按存储粗估，256,000 个粒子、每粒子 256 个字节的顶点词本身约 64 MiB；
双粒子群、resampling/CDF 与临时工作区会继续增加。真正瓶颈则是计算量：若仍用
`P=262144,R=256,L=16`，每根约有
\(P R L (N-2)\approx2.73\times10^{11}\) 个 MH 提案，现行线性扫描实现不可接受。

因此 n=16 需要独立的多 limb 状态表示、完整范围/溢出审计以及 proposal/valid
数据结构重设计和小 n 字节级回归后，才可作基准测试；这不是本源码的简单内存或
参数扩张。

建议的最小规范路径是：独立新实现使用 `std::bitset<256>` 或 4×`uint64_t`，
以 log-normalizer/逐层归一化表示；先完整核对 n=3、n=4 的所有根计数，并与旧核
在相同种子和小 n 参数下逐轨迹回放一致，再运行 n=16 小 P 校准。当前 GPU 一峰
n=16 批的粒子权重 ESS 仅 6.605/128、最大份额 0.3701，说明固定根/D4 分层可作为
候选方差缓解方向；但它不替代上述 CPU 新核的正确性或数值稳定性认证。
