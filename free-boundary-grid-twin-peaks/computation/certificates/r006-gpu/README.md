# r006 GPU handoff — batch construction search

Status: finite numerical construction search only.  No frequency below is an
estimate of \(\mathbb P(\cdot\mid K_n=2)\), and no entry is a proof of an
asymptotic lower bound.

* Matching executable: `twin_peaks_gpu_accepted_audit`, SHA-256

The final source uses an in-process Metal shader.  It validates GPU peak
counts against CPU peak counts for **every initial chain**, and the Python
annotator recomputes `K=2`, peaks, distance, \(\beta\), first-merge label and
gradient-basin interface for every saved label matrix.

Compile reproducibly (module cache deliberately on the data volume):

`proposal` means one attempted swap in a seeded GPU chain.  The historical JSON field `gpu_seconds` measures wall time from command-buffer commit through waitUntilCompleted, including queueing and synchronization. It is not hardware-only GPU execution time.

Thus V1+V2 (before the accepted-move audit) comprises exactly
**2,080,374,784** proposals and **164.8021237850189222** submission-to-completion wall seconds.  V3 is
an **additional**, not overlapping, **268,435,456** proposals and
**27.884579300880432** seconds.  Grand total: **2,348,810,240** proposals and
**192.6867030858993542** submission-to-completion wall seconds.

V1 had the mixed initial population and no `--cut-only` option.  V2 added
the cut-only no-temperature kernel but did not retain an accepted-move output
buffer.  V3 is the frozen source/executable here; relative to V2 it adds only
the per-chain accepted-swap output buffer and JSON field.  The raw V1/V2
records must therefore not be described as output of the V3 binary.

## Saved records and CPU audit

Raw records retain every saved full labeling and their original summary:

* `gpu-search-n8.jsonl` (V1)
* `gpu-search-random-n12-32.jsonl` (V1)
* `gpu-search-cut-n24.jsonl`, `gpu-search-cut-n32.jsonl` (V2)
* `gpu-search-results.jsonl` (V3 only; n=24 accepted audit)

The corresponding `*-annotated.jsonl` files were regenerated by the frozen
Python verifier.  They cover respectively 8, 9, 64, 64 and 64 saved matrices;
all satisfy its independent `K=2` and stated-distance checks.  The two n=24
cut annotated outputs happen to hash identically: this is an observed label
coincidence for the saved first 64 records, not an assertion that V2 and V3
are the same binary trajectory.

For the 64 CPU-audited cut-only samples: n=24 distance range 23–45 (mean
32.171875), first-merge label range 130–414, gradient-basin interface edges
27–39, and all \(\beta=0\).  n=32 distance range 32–60 (mean 41.84375),
first-merge label range 241–742, interface edges 33–52, and all \(\beta=0\).
The current useful construction search thus remains within a low-\(\beta\)
rectangular-type family; it supplies no normalized mass lower bound.

## GPU-activity evidence and shutdown

`powermetrics` required administrator authentication and was unavailable.
During the n=32 cut-only batch, unprivileged `ioreg -r -c AGXAccelerator -l`
samples gave the following actual `PerformanceStatistics` fields:

```
Tiler Utilization %=3, Renderer Utilization %=100, Device Utilization %=100
Tiler Utilization %=1, Renderer Utilization %=97,  Device Utilization %=99
```

These are system AGX samples, not per-kernel attribution, but were observed
while the recorded n=32 process was active.  After final annotation, `ps`
matched no `twin_peaks_gpu` or `powermetrics` process; GPU resources are not
left resident by this work.
